# 创建档案时如何处理重复 HTTP 请求

客户端调用 `POST /api/v1/profiles` 后，数据库可能已经提交，但响应在网络中丢失。以前客户端重发相同正文时，档案唯一约束会返回 `409`；客户端仍不知道第一次创建的档案 ID。消息 Inbox 只处理消息重复投递，不处理这类 HTTP 重试。

这里有两个独立的选择。`Http:Idempotency:Enabled` 默认是 `false`，决定宿主是否注册幂等存储和清理任务，以及就绪检查是否要求幂等迁移。接口还必须在映射时显式调用 `.RequireHttpIdempotency()`；Reference 只给 `POST /api/v1/profiles` 做了这个标记。把全局开关设为 `true`，不会让未标记的接口自动处理 `Idempotency-Key`。

| 全局开关 | 端点标记 | 请求头 | 结果 |
| --- | --- | --- | --- |
| 关闭 | 已标记 | 任意值 | 沿用普通创建流程，不校验请求头。 |
| 开启 | 已标记 | 无 | 沿用普通创建流程，不查询幂等表。 |
| 开启 | 已标记 | 有 | 校验请求头，并按下文查询、占位或重放。 |
| 开启 | 未标记 | 任意值 | 沿用该接口原有流程，不校验请求头。 |

例如全局开启后，带有效键的创建档案请求成功返回 `201`；同一身份用相同键和正文重试，会得到第一次的响应。`PATCH /api/v1/profiles/{id}` 没有标记，即使附带格式错误的键，仍按版本号处理更新。全局关闭时，已标记的创建端点也忽略键；同一个创建请求重发，仍可能因档案唯一约束得到 `409`。

原实现把全局开关同时用于基础设施注册和创建端点的处理方式：一旦开启，创建端点就走带键处理器，没有路由级的明确选择。现在标记只给选中的端点接入幂等处理；未标记端点不经过检查 Method、Path 和配置的全局 Middleware，也不解析幂等请求头。全局关闭时，宿主不注册幂等存储和清理任务，创建请求不查询幂等表。就绪检查只忽略 SelfManaged 和 Wolverine 各自已知的 `AddHttpIdempotency` 迁移；其他业务和消息迁移仍须应用。关闭功能的部署因此不必为了处理创建请求而安装幂等表。

当前 `.RequireHttpIdempotency()` 是 Reference.Web 内部针对创建档案端点的映射方法，复用这个端点已有的事务和响应序列化代码。它不能直接贴到任意其他业务端点；新的写入操作需要先明确自己的请求指纹、事务和可重放响应，再为该端点接入。

开启前，先通过独立迁移器应用所选消息提供者对应的幂等迁移。宿主不会自动建表。全局开启且端点已标记时，客户端可以为一次创建操作发送一个 `Idempotency-Key`。端点检查该请求头只能有一个值，且它是 1–128 个可见 ASCII 字符，不含逗号；没有请求头时仍按原来的创建流程执行。幂等范围由固定操作名、已验证令牌的 issuer 和 subject、请求键共同决定；不同认证身份即使用同一个键，也看不到对方的响应。请求指纹来自已绑定的 `CreateProfile` DTO，经源码生成的 JSON 元数据序列化后计算 SHA-256。JSON 属性顺序和空白差异不会影响该 DTO 的表示；角色数组顺序不同则被视为不同请求。绑定器忽略的未知 JSON 字段不进入指纹；发布时若修改 DTO 或序列化方式，要核对保留期内旧请求的重试兼容性。

已标记端点的首次带键请求先查记录。相同指纹的已完成记录直接返回保存的 `201`、`Location` 和正文字节；同一个键配不同请求得到 `409`。查不到记录时，消息 `IUnitOfWork` 开启外层数据库事务，幂等存储先插入唯一键占位记录并刷新到数据库，再调用 `ProfileService.CreateAsync`。服务内部的嵌套工作单元参加同一事务；由同一工作单元提交档案、出站消息和响应记录。如果做一个在普通处理器结束后才保存响应的通用过滤器，这三项就无法在当前事务内一起提交；因此路由标记复用现有的创建档案事务处理。响应正文只序列化一次，首次响应和重放都从同一个快照写出。

当前 `ProfileService.CreateAsync` 的校验或业务冲突结果没有持久化副作用。它返回 4xx 错误时，端点让外层事务回滚占位记录，再由 `ApplicationErrorResults` 写出原有 ProblemDetails。同一个无效请求不会占用键；修正请求后可重用该键。异常、取消和 5xx 也不留下记录。**只有创建成功的 `201` 会保存并重放。**记录的保留期为 24 小时；启用时，宿主每小时调度清理。到期但尚未删除时仍重放，删除后同键可以再次执行。客户端应在最早可能清理记录之前完成重试。

启用期间如果幂等迁移未应用，无键请求仍走原有流程；带键请求查询幂等表会失败，就绪检查也会报告待迁移。清理任务会先检查迁移状态，未就绪时静默跳过，不会自行创建或修改数据库表。关闭功能不会删除旧响应记录，也不会继续清理它们。重新启用前应清理到期记录；若暂不清理，已过期的记录在首次清理周期到来前仍可能重放。

两个请求同时使用同一键时，数据库唯一约束只允许一个先取得占位记录。另一个请求的工作单元退出并回滚后，端点用**新的依赖注入作用域和 DbContext**查询赢家结果；相同请求返回赢家快照，不同请求返回 `409`。如果仍查不到记录，保留原数据库异常，不能把连接故障或其他写入失败假装成幂等键冲突。

幂等记录存请求键和身份的哈希，不存原始键；响应正文仍可能包含个人数据，应按业务数据管理。该保证只覆盖同一数据库事务中的档案和消息 Outbox，不覆盖事务外的网络调用。此次接入没有增加对运行时反射的调用，仍使用现有的源码生成 JSON 元数据；未标记接口不执行幂等过滤器。SelfManaged 的 SQLite 测试覆盖了同事务路径；Wolverine 原生 Outbox 及两种实现的 PostgreSQL 并发与恢复仍需实际依赖环境验证。没有这次改动前后的性能基线，不能据此声称延迟或分配已降低。

目前两种 Reference DbContext 仍在 EF 模型中映射幂等表，通用迁移器执行全部迁移时仍会创建它。关闭开关只解除运行时对该表的依赖；若部署选择暂不建表，需要把迁移停在对应的 `AddHttpIdempotency` 之前。将来若在它后面增加新的必需迁移，就不能继续依靠跳过当前迁移来保持无表部署；届时应考虑把幂等表移到独立迁移流，再分别验证两种消息提供者的升级路径。
