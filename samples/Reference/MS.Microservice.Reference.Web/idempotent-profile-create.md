# 创建档案时如何处理重复 HTTP 请求

客户端调用 `POST /api/v1/profiles` 后，数据库可能已经提交，但响应在网络中丢失。以前客户端重发相同正文时，档案唯一约束会返回 `409`；客户端仍不知道第一次创建的档案 ID。消息 Inbox 只处理消息重复投递，不处理这类 HTTP 重试。

客户端可以为一次创建操作发送一个 `Idempotency-Key`。端点先检查该请求头只能有一个值，且它是 1–128 个可见 ASCII 字符，不含逗号。没有请求头时仍按原来的创建流程执行。幂等范围由固定操作名、已验证令牌的 issuer 和 subject、请求键共同决定；不同认证身份即使用同一个键，也看不到对方的响应。请求指纹来自已绑定的 `CreateProfile` DTO，经源码生成的 JSON 元数据序列化后计算 SHA-256。JSON 属性顺序和空白差异不会影响该 DTO 的表示；角色数组顺序不同则被视为不同请求。绑定器忽略的未知 JSON 字段不进入指纹；发布时若修改 DTO 或序列化方式，要核对保留期内旧请求的重试兼容性。

首次带键请求先查记录。相同指纹的已完成记录直接返回保存的 `201`、`Location` 和正文字节；同一个键配不同请求得到 `409`。查不到记录时，消息 `IUnitOfWork` 开启外层数据库事务，幂等存储先插入唯一键占位记录并刷新到数据库，再调用 `ProfileService.CreateAsync`。服务内部的嵌套工作单元参加同一事务；设计目标是由同一工作单元提交档案、出站消息和响应记录。响应正文只序列化一次，首次响应和重放都从同一个快照写出。

当前 `ProfileService.CreateAsync` 的校验或业务冲突结果没有持久化副作用。它返回 4xx 错误时，端点让外层事务回滚占位记录，再由 `ApplicationErrorResults` 写出原有 ProblemDetails。同一个无效请求不会占用键；修正请求后可重用该键。异常、取消和 5xx 也不留下记录。**只有创建成功的 `201` 会保存并重放。**记录的保留期为 24 小时；到期记录由宿主每小时调度清理。到期但尚未删除时仍重放，删除后同键可以再次执行。客户端应在最早可能清理记录之前完成重试。

幂等表依赖独立的数据库迁移器。迁移未应用时，无键请求仍走原有流程；带键请求查询幂等表会失败，宿主的就绪检查也会报告待迁移。清理任务会先检查迁移状态，未就绪时静默跳过，不会自行创建或修改数据库表。

两个请求同时使用同一键时，数据库唯一约束只允许一个先取得占位记录。另一个请求的工作单元退出并回滚后，端点用**新的依赖注入作用域和 DbContext**查询赢家结果；相同请求返回赢家快照，不同请求返回 `409`。如果仍查不到记录，保留原数据库异常，不能把连接故障或其他写入失败假装成幂等键冲突。

幂等记录存请求键和身份的哈希，不存原始键；响应正文仍可能包含个人数据，应按业务数据管理。该保证只覆盖同一数据库事务中的档案和消息 Outbox，不覆盖事务外的网络调用。SelfManaged 的 SQLite 测试覆盖了同事务路径；Wolverine 原生 Outbox 及两种实现的 PostgreSQL 并发与恢复仍需实际依赖环境验证。这里改变的是写入正确性，没有可对比的性能基线，也不声称请求更快。
