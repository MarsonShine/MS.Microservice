# 静音写入：输出长度不等于工作缓冲大小

原实现每处理一个音频源，就为后面的静音创建一个完整零数组。默认 44.1 kHz、16 bit、双声道的一秒静音需要 `44100 × 2 × 2 = 176400` 字节；100 段便产生 17,640,000 字节的临时数组内容，不包括数组对象头。

当前零填充路径的内容始终相同，没必要先在内存中展开全部零字节。`Stream.Write` 可以多次写入同一块缓冲，因此新实现共享一个私有的 4 KB 零数组，重复写出，最后一块只写剩余字节。

## 缓冲放在哪里，决定了能否真正复用

WAV 和 MP3 写入器只读取输入数组，零块本身没有游标，可以供不同合并操作复用。缓冲由类初始化一次；调用者只提供输出、格式和时长。

```csharp
private static readonly byte[] SilenceBuffer = new byte[4096];

// 每写完一个音频源：
WriteSilence(writer, targetFormat, durationSeconds);
```

这里共享的是字节数组，不是 `MemoryStream`。流对象有 `Position` 和释放状态，共享它会引入重置与并发读取问题。每个调用仍独立计算 `remaining`，写入自己的输出流；共享数组不意味着同一个写入器可以被并发操作。

`readonly` 只限制引用重新赋值，不能冻结数组内容。因此数组保持私有，不作为音频读取缓冲，也不交给会修改输入数组的实现。测试会验证不同输出流并发读取时，零内容与各自长度均保持正确。

不再需要 `ref`：它原本只是把首次创建的数组引用写回调用者变量，供下一段复用，从来不负责拼接音频。现在数组直接由类持有，输出拼接仍由连续的 `Write` 完成。

普通小数组已经满足这里的需求；引入数组池还需要管理归还和清零，本实现没有增加这些职责。

## 分块不能改变格式、时长或位置

- 沿用原来的 float 乘法、整数样本数截断、乘每样本字节数的顺序。不能为了凑齐 4 KB 把尾块补满，否则会增加静音时长。
- 保持每个音频源之后的静音，包括最后一个源之后的静音。零时长或取整后为零字节时，不执行写入。
- 传入的 `writer` 仍是 `WaveFileWriter` 或 `LameMP3FileWriter`。写给 MP3 编码器的是 PCM 零字节，不能绕过编码器直接向 MP3 文件追加零字节。[编码器的 Write 实现](https://github.com/Corey-M/NAudio.Lame/blob/master/NAudio.Lame/LameMP3FileWriter.cs)本身会累积输入分块。
- 字节计数使用 checked，无法用原有 int 范围表示的长度在写入前失败，避免溢出后循环静默少写；没有扩展超长时长的支持范围。

输出仍采用旧代码的零字节填充语义。本主题不重新定义各音频编码的静音表示。

## 验证的是输出契约和工作缓冲

[生产测试](../../../test/MS.Microservice.Audio.Tests/SilenceBufferTests.cs)验证零时长、极短和分数秒、整块与尾块、不同位深/声道以及长静音。记录流检查总字节数、全零内容、最大写入块和缓冲身份，不需要音频设备。

WAV 测试通过公开合并接口检查原音频与静音的准确位置。MP3 测试使用同一个版本的编码器，比较整段写入与分块写入产生的编码字节。写入失败还应原样传播，流的释放仍由调用方负责。

预热后的分配测试连续写出 100 段默认一秒静音，要求该路径分配低于 1 KB，并检查不同输出流读到的是同一个数组。类型初始化时的一次 4 KB 数组分配不计入预热后的测量。测试使用不保存输出的记录流，避免把输出容器的扩容算成静音工作缓冲。

返回 `byte[]` 或 `MemoryStream` 的接口仍需保存实际输出，编码器也有自己的缓冲；本改动不代表整个合并过程只占 4 KB，也不保证每种目标流的总分配和耗时都按相同比例下降。共享零数组随类型生命周期保留。

`Legacy/SilenceWritingExample.cs` 与 `Static/SilenceWritingExample.cs` 用标量格式参数独立展示两种写法；[对照测试](../../../test/MS.Microservice.Lab.AotExamples.Tests/SilenceWritingExampleTests.cs)检查相同字节输出和分块差异。这是运行时分配优化，不构成 AOT 发布验证。
