# 缓存与 HTTP JSON 元数据复用

## 问题与原因

最早的缓存读取已经从后端拿到完整的 JSON `byte[]`，仍为每次读取创建 `MemoryStream`、`JsonSerializerOptions` 和 Unicode 编码器。缓存写入与 HTTP JSON 读取也在每次调用时创建相同的配置。固定格式规则和类型元数据反复准备，增加托管堆分配。

缓存与 HTTP 的规则不同：缓存读取区分属性名大小写，HTTP 读取不区分大小写；缓存遇到无效 JSON 抛出异常，HTTP 辅助方法返回默认值。调用方必须为这两种规则提供相应的 JSON 契约。

## 本次方案

当前 AOT 分支的缓存和 `MS.WebHttpClient` 接口接收调用方提供的 `JsonTypeInfo<T>`。调用方可从源码生成的上下文取得它；辅助类按此元数据序列化或反序列化，不再自行创建 `JsonSerializerOptions`，也不在缺失元数据时回退到反射。缓存直接解析后端返回的字节，避免包装 `MemoryStream`；HTTP 继续从响应流异步解析。各次调用只复用类型元数据，不共享业务数据。

直接解析字节与原流解析有两个边界差异：流解析接受开头的 UTF-8 BOM，Span 解析前需跳过该前缀；Span 解析没有取消参数，因此缓存读取在解析前后检查取消。缓存字节既不复制也不修改，BOM 不在开头时仍视为无效 JSON。

早期性能切片 `52abd2d` 曾在辅助类内复用私有 `static readonly JsonSerializerOptions`，保持原公开签名。后续 AOT 迁移改为显式 `JsonTypeInfo<T>` 参数，公开签名已变化；不能把早期的无元数据重载合并回来，否则会恢复运行时类型发现。

## 测量与验证

原性能切片 `52abd2d` 在 .NET 10.0.12、Debug、内存后端和小型 DTO 下预热 32 次，再测量 64 次，记录了以下单次分配。这是早期 `JsonSerializerOptions` 复用方案的结果，不是当前 `JsonTypeInfo<T>` 方案的前后对比，也不代表网络吞吐量。

| 路径 | 修改前 | 修改后 |
|---|---:|---:|
| 缓存读取 | 45,809 B/次 | 400 B/次 |
| 缓存写入 | 49,825 B/次 | 576 B/次 |
| HTTP JSON 读取 | 48,043 B/次 | 2,576 B/次 |

合并时在当前 AOT 分支工作树以 .NET 10.0.12、Release 运行相同的预热与采样方式，缓存读取为 296 B/次、缓存写入 464 B/次、HTTP JSON 读取 2,288 B/次。没有在相同 Release 条件下运行 AOT 接口修改前的实现，因此不把这些数字与上表直接相减，也不据此声称 AOT 接口比早期复用方案更快。

`JsonReuseRegressionTests` 使用生成上下文检查预热后的分配，并覆盖属性名大小写、中文转义、null、枚举、嵌套值、缓存失效行为、无效 JSON、取消、BOM 与并发调用。分配断言留有余量，避免把某个运行时版本的精确字节数当作契约。
