# Audio 处理性能验收

2026-11-20，比较基线 `4a735c7` 和工作区的 Release 构建。环境为 Windows 10 x64、Intel Core i5-9400、.NET SDK 11.0.100、运行时 11.0.0。

样本如何按块写入，以及每段分配的 4 KiB 如何累加，见[模块性能笔记](../../../src/MS.Microservice.Audio/docs/wav-processing-performance.md)。

## 对照方法

[基准程序](../../../benchmarks/MS.Microservice.Audio.Benchmarks/ProcessingBenchmarks.cs)调用生产公开 API。混音使用单声道与立体声各一个输入，声道转换使用单声道输入，编辑使用立体声输入。这些 PCM16 文件均为 44.1 kHz、8 秒加 17 帧，可覆盖最后一个不足整块的写入。编辑增益为 1.375，淡变场景额外设置 1.5 秒淡入、2.25 秒淡出。合并使用 128 段各 127 至 254 帧的不同单声道 PCM16 数据，同格式输出 WAV，静音时长设为零。

运行 `dotnet run --project benchmarks/MS.Microservice.Audio.Benchmarks -c Release -- --processing` 可以复测当前版本。复现前后对照时，将相同的基准文件放入基线检出目录，或在相同的基准构建产物中替换为基线版本的 `MS.Microservice.Audio.dll`。

每组预热 4 次，再测 7 轮，每轮 4 次。耗时包括线程池调度、读写、处理和输出关闭，输入准备、删除上次输出和计算 SHA-256 在计时之外。分配使用 `GC.GetTotalAllocatedBytes(true)` 的进程差值，包含工作线程。缓冲池保留的容量、原生编解码器内存和进程峰值需另行测量。

## 结果

基线和最终版本各启动三个独立进程，顺序为旧、新、新、旧、旧、新。表中为三个进程各自报告的中位数再取中位数。五组场景的输出均在全部六次运行中得到相同的 SHA-256。

| 公开入口与输入 | 耗时，旧 → 新（ms/次） | 托管分配，旧 → 新（B/次） | 输出 SHA-256 前 12 位 |
| --- | ---: | ---: | --- |
| 两路 WAV 混音 | 41.005 → 17.564 | 69,896 → 53,520 | `4C8F2596508B` |
| 单声道转立体声 WAV | 21.581 → 11.744 | 39,440 → 23,064 | `68D2F2687AC8` |
| 128 段 PCM 合并至 WAV 文件 | 2.174 → 1.854 | 621,864 → 102,808 | `F7F2B40AF908` |
| 编辑，仅增益（对照） | 13.400 → 13.735 | 52,072 → 52,072 | `55FBFCED5698` |
| 编辑，增益与淡变（对照） | 13.655 → 13.734 | 52,072 → 52,072 | `604510336113` |

混音和声道转换原先通过 NAudio 逐样本写浮点 WAV。现在按实际读到的样本数整块写入，并从标准数组池租用缓冲区，使用完毕后清零归还。每次合并在所有输入间复用一个 4 KiB 读缓冲。向同一个 WAV 文件合并多个输入时，短写入先合批，减少 WAV 写入器查询文件长度的次数。

编辑器的候选实现尝试共用浮点与字节缓冲、调整读写块大小，降低了分配，但两种编辑场景的端到端耗时都未稳定改善，最终保留基线实现。性能数字仅覆盖表内的本机 WAV 工作负载。

## 行为验证

- `dotnet test test/MS.Microservice.Audio.Tests -c Release` 通过 93 项，失败 0 项，跳过 0 项。新增的混音用例逐样本验证声道顺序、超出 ±1 的浮点值与最后一个不满的块。已有的多输入用例补充比较了带重采样和静音的文件输出与内存输出。
- 在 Windows 上额外调用返回字节数组的 `CombineAudioDataAsync`，将三段不同长度的 44.1 kHz 立体声 PCM16 合并，每段后附 0.125 秒静音。前后两版生成的 MP3 均为 16,277 字节，WAV 均为 140,216 字节，各自的 SHA-256 一致。
- 为隔离读缓冲的分配，在 .NET 11 x64 Release 下将 `CopyAudioData` 绑定为委托，预先创建输入和足够容量的内存输出流。两组分别预热后，在同步线程上连续复制 128 段，每段 4 字节。使用 `GC.GetAllocatedBytesForCurrentThread()` 记录整组分配，含复用组在循环前创建的数组。三轮均为每次传 `null` 分配 527,360 B，复用同一数组分配 4,120 B。两组每次都校验了全部 512 个输出字节。此实验不含编解码或磁盘写入。
- 在 .NET 11.0.0 和 NAudio 2.2.1 下复用同一个 4 KiB 读数组，依次写入内容不同的 300、500、200 B 三段 PCM16。记录进入 `WaveFileWriter.Write` 的数据长度，直接写为 300、500、200 B，加写缓冲后三段在关闭时合为 1000 B。使用基准的 128 段长度时，调用由 128 次变为 12 次（11 × 4096 B + 3712 B）。两组对照各自的完整 WAV 均逐字节相同。
- 使用混音尾块测试中的 6 个浮点样本，按 4、2 个分批写入。只在音频数据写入期间记录 WAV 写入器下层流的调用，旧版 `WriteSamples` 产生 6 次 4 B 写入，小端块写产生 16 B、8 B 两次写入。两条路径生成的 82 B WAV 逐字节相同，读回 24 B 音频数据与全部原始样本一致。
- 源码对照笔记的行号链接已逐一匹配目标语句，前后代码摘录已与基线和工作区核对。答题卡示例实际运行输出 `2`、`0`，`git diff --check` 通过。
