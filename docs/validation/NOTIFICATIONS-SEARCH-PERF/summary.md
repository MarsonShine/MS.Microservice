# 通知组件的性能验收

2026 年 11 月 23 日，在同一台 Windows 10 x64 机器上比较基线 `4ba9bd9` 和本次修改。[通知性能笔记](../../../src/MS.Microservice.Notifications/docs/notification-performance.md)

## 复测方法

硬件为 Intel Core i5-9400，SDK 为 .NET 11.0.100，使用 Release 构建和热文件缓存。每个模块的新旧程序集分别装入同一份基准程序，以旧新、新旧、旧新的顺序交错启动六次进程。每个场景先预热一批，再测七批，取各版本三个进程的批次中位数的中位数。时间含单次公开调用的全部工作；`GC.GetTotalAllocatedBytes(true)` 统计进程内的托管分配，包含异步 I/O 的工作线程。它不度量进程峰值内存、操作系统缓存或常驻索引大小。

```powershell
$env:DOTNET_TieredCompilation = '0'
dotnet run -c Release --project benchmarks/MS.Microservice.Notifications.Benchmarks
```

## 收件箱和模板

本地临时目录内发布 128 封通知，每封正文为 2048 个 ASCII 字符。先读取全未读页，再把每隔一封标为已读。比较完整页面内容、排序及全局的总数和未读数；重复标记时还核对最初的时间戳。每批分别测 2 次列表、16 次标记、4096 次模板调用。[基准源码](../../../benchmarks/MS.Microservice.Notifications.Benchmarks/Program.cs)

| 操作 | 旧 µs/次 | 新 µs/次 | 旧 B/次 | 新 B/次 |
| --- | ---: | ---: | ---: | ---: |
| 纯文本模板 | 0.298 | 0.081 | 2400 | 0 |
| 两个变量，HTML 编码 | 0.290 | 0.310 | 312 | 232 |
| 全未读，取首页 8 封 | 118941.500 | 91815.000 | 12829368 | 817208 |
| 半数已读，取首页 8 封 | 139402.950 | 127184.550 | 18267124 | 885816 |
| 半数已读，跳过 120 封再取 8 封 | 143316.850 | 126252.250 | 18267196 | 889676 |
| 半数已读，一次取全部 128 封 | 142790.250 | 124878.700 | 18268084 | 890636 |
| 再次标记一封已读通知 | 908.506 | 763.675 | 92528 | 3620 |

首页与全页的分配都下降，说明即使必须返回全部正文，共用字节工作区仍有收益。两个短 HTML 占位符的耗时上升了 0.020 µs，同时减少了 80 B 分配。模板输入和替换字典在计时前创建。

## 邮件和短信的测量边界

短信通过公开 `AliyunSmsSender.SendAsync` 验证本地请求开销。32 个合法变量配上 1 B 总预算，方法必须在提交给 SDK 前抛出字节预算异常。每批 256 次，耗时 15.146 → 14.729 µs/次，分配 4992 → 4080 B/次。传入 `--sms-only` 可以单独复测。[短信基准入口](../../../benchmarks/MS.Microservice.Notifications.Benchmarks/Program.cs)

另用局部探针测成功准备参数的情况。8 个变量时，检查、快照、JSON 序列化和构造 SDK 所需字符串合计 3.853 → 3.536 µs，2416 → 1864 B；32 个变量时为 14.029 → 13.675 µs，7504 → 6592 B。每组预热两轮、交错测十一批，每批 768 次，取三个进程的中位数。该探针在准备出字符串后停止。SMTP 则核查了消息构造、信封收件人、TLS、单次连接与接受后清理的调用链；现有回环测试覆盖真实协议交互。两种发送通道都没有测量外部服务的响应或最终投递延时。
