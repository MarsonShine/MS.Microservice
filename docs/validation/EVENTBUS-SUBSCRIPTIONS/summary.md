写入组的一次操作覆盖表中所写的整个周期。例如“八个处理器全部注册再注销”包含 16 次 API 调用。并发组则以整批墙钟时间除以所有读写调用的总数，得到吞吐的摊销时间。四个逻辑读者的每次摊销时间可以低于一个读者的单次调用时间，其中包含任务调度。单线程命中和未命中均使用与注册键内容相同或不同、但独立构造的查询字符串。

每种场景先预热一批，然后测 7 批，每个进程分别取耗时和分配的中位数。单线程写入每批运行 4096 个周期，单读者每批查询 65,536 次。并发使用最多四个工作线程，读者每批各查 65,536 次，写者每批各注册和注销 4096 次。分配用 `GC.GetTotalAllocatedBytes(true)` 的进程差值。约 0.01 B/op 是把调度等批次分配摊入大量操作后的结果。预热和批后校验在计量区间外。[基准程序](../../../benchmarks/MS.Microservice.EventBus.Benchmarks/Program.cs)

新旧版本共用同一份基准程序与依赖，只替换 `MS.Microservice.EventBus.dll`。以旧、新、新、旧、旧、新顺序分别启动独立进程，表中取同一版本三个进程中位数的中位数。关闭分层编译以减少短调用在测量途中切换 JIT 层级的影响。可在仓库根目录运行：

```powershell
$env:DOTNET_TieredCompilation = '0'
dotnet run --project benchmarks/MS.Microservice.EventBus.Benchmarks -c Release
dotnet test test/MS.Microservice.EventBus.Tests -c Release
```

## 怎样解读内存数字

对于八种各只有一个处理器的事件，旧版要为每种事件创建一个集合。新版直接在各自的订阅条目里保存首处理器。对于同一事件的额外处理器，管理器共享一个按“绑定事件类型、处理器类型”去重的集合，预热后可以重用容量。新管理器立即注册两个处理器时，仍需首次建立这个额外集合，实测总分配与旧版相当。不要把稳态循环的 88 B 当成新建管理器的成本。

逐项注销后，已经申请的索引容量可以继续驻留，直到 `Clear` 放开两个索引或者管理器被回收。本表测量每次操作累计产生的托管分配，没有测量进程峰值、GC 暂停、远程消息延迟或业务处理器耗时。“八个不同事件名注册后清空”的耗时差约 1%，其主要收益在分配。
