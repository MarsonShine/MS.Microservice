# CSV 写入性能与取消验收

2026-11-23。在同一台 Windows 10 x64、Intel Core i5-9400、.NET SDK 11.0.100 的机器上对比基线 `bfa3011` 和实现 `1b02b69`。范围覆盖 `CsvHelper.WriteAsync` 和通过它导出模型的 `ExportCsvAsync`。[对照代码与缓冲示意图](../../../src/MS.Microservice.Excel/docs/csv-performance.md)

## 完整导出的耗时与分配

两版使用同一个 [CSV 基准程序](../../../benchmarks/MS.Microservice.Excel.Benchmarks/CsvCases.cs)。在 Release 输出目录仅替换 Excel 模块 DLL，使用 `DOTNET_TieredCompilation=0`，新旧各启动五个进程，交替调整先后顺序。每个场景预热一批，然后测七批，表中取各进程中位数的中位数。输入提前构造，重复使用容量足够的 `MemoryStream`，每批验证最后一次导出的完整 UTF-8 字节。`B/次` 为每次导出期间的托管分配量，排除输入构造，包含写入器和编码缓冲区。测量当前版本可运行：

```powershell
$env:DOTNET_TieredCompilation = '0'
dotnet run -c Release --project benchmarks/MS.Microservice.Excel.Benchmarks -- --csv-only
```

同槽的两个分隔符轮流驱逐对方，每次导出都要检查缓存并重新建表，这组短导出多花了 0.173 µs。缓存最多保留 16 张不可变的表；分隔符数量、导出并发度和不同槽的命中率会影响实际收益。按块合批复用了原来的工作区，所以短行场景的分配量持平。普通长字段的写入代码也沿用基线，两个逗号对照场景的耗时略有上升。以上数字仅覆盖内存流，未测磁盘或网络延迟、常驻内存或峰值内存。

## 具体省去了哪一步

- **跨行合批**。临时计数探针在两版源码的 `StreamWriter.WriteAsync` 调用点计数，并在目标流上分别统计写入和刷新。1024 行 `x\r\n` 的字符层提交次数为 **1024 → 1**；两版的目标流均收到 **1 次 3072 B 的写入和 2 次刷新**。各自输出都与期望字节完全一致。
- **引号密度**。用 2048 个 UTF-16 码元单独比较逐字符双写与 `IndexOf + CopyTo`，调换测量顺序，每种分布各测七批、每批 512 次。等距引号间隔为 8 时分别为 1752 和 2141 ns/片，间隔为 16 时分别为 1638 和 1231 ns/片。每个间隔内随机放置引号时，间隔 8 为 2307 和 2370，间隔 16 为 2210 和 1273 ns/片。两种分布在 16 都体现了跳段收益，代码据此复用预算检查已算出的引号数来选择路径。
- **取消粒度**。将相同回归测试装载到旧 DLL，65,536 个普通字符与 65,536 个引号的两个用例原本都通过。在目标流忽略令牌、成功写入首块后取消的条件下，两例均在最多 8192 个 ASCII 输出字节内结束，包含释放写入器时可能排出的缓冲数据。尝试把可取消的普通长字段再分段直写，16384 个普通字符从 3.737 增至 4.227 µs/次，因此保留原来的整段直写。行末触发取消的回归测试在旧版得到源枚举器的 `InvalidOperationException`，新版在下一次 `MoveNext()` 之前抛出携带原令牌的 `OperationCanceledException`。对于应用自己执行的转义循环，还在每个最多 2048 个码元的片段开始处检查取消。一次阻塞 I/O 的耗时由目标流决定。

- 临时差分探针使用固定种子 542819，对新旧 DLL 分别传入默认令牌和可取消但未触发的令牌，各比对 2048 组。合计 2978 份成功输出逐字节一致，746 组 CSV 格式错误的类型与逻辑行列一致，372 组编码错误的类型一致，所有目标流在返回后仍可写。输入涵盖六种分隔符、三种行结束符、四种编码配置、BOM、记录预算，以及 UTF-16 代理对跨块的长字段。失败场景允许部分输出，只对照错误契约。
